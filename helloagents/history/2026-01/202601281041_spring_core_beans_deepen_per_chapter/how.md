# how：逐章“深度完善”的执行策略（不套固定标准）

## 总体策略：以“逐章评审”驱动内容深化

这次不做“统一标准”或“固定模块补齐”，而是对每章做一次类似 Code Review 的评审，输出三类东西（每章各不相同，按章取舍）：

1) **机制深化**：把本章核心机制补到“能解释为何如此”的深度  
   - 不是堆概念，而是把关键分支/数据结构/算法讲清楚（必要时给伪代码/流程拆解）
2) **边界深化**：把本章的“能/不能”讲成可推导结论  
   - 用反例与误归因对照源码分支，让读者能在新场景里推导结论
3) **真实世界深化**：补齐与 Boot/AOP/Tx/Environment/AOT 的交叉点  
   - 只补“高频且容易踩坑”的交叉点，避免写成百科

> 说明：不新增专门的“与上一章/下一章桥接小节”。本方案的改动重心只放在**该章内容本身的知识详解与机制深挖**；章节之间的连续性只通过必要的术语一致性与引用保持。

> 重要：上述三类并非每章都要全做，本方案的 `task.md` 会按章节内容给出“该章需要补什么、怎么补”的定制策略。

## 推进方式：分批落地、批次内保持闭环

推荐按“机制域”分批推进（每批 5–10 章），每批都做三件事：

- **内容落地**：按 `task.md` 对选定章节实施深化（文档为主，必要时补 Lab/Test）
- **交叉一致性回归**：检查本批章节与相邻章节的互链、术语一致性、对同一概念的描述是否冲突
- **可运行回归**：如果本批新增/修改了 Lab/Test，则运行本模块测试，确保教学闭环可用

## 章节深化的常用“抓手”（按章选用）

为了让“深度完善”可落地，本方案建议优先用这些抓手（不要求每章都用）：

- **算法化表达**：把关键决策过程表达成“输入 → 过滤/收敛 → 输出”的步骤（适用于候选选择、排序、合并、解析等章节）
- **分支树**：把某个关键方法拆成分支树：每个分支对应一个常见现象/报错（适用于排障型章节）
- **对照实验**：同一机制至少给出 1 个对照（A vs B），让边界可被验证（适用于循环依赖、代理、Scope、@Value 等章节）
- **跨章锚点**：同一个关键类/方法只在“主讲章节”讲透，其他章节引用并给出最小补充（避免重复堆字）

## 风险控制（避免越写越散）

- **避免百科化**：每章只补“这章应当更深一层的关键点”，其余内容用链接跳转到主讲章节
- **避免重复**：遇到重复概念，统一到“主讲章节”，其他章节只给“1 句提示 + 1 个锚点链接”
- **避免空泛**：所有新增内容必须落到“具体机制/具体分支/具体反例/具体排障路径”，杜绝口号式段落

## 验证与回归（后续实施阶段）

本方案执行时建议采用以下回归方式（按批次执行）：

- 文档侧：运行 Markdown 链接存在性检查（若仓库已有脚本则复用）
- 代码侧：运行 `spring-core-beans` 模块的测试（仅当本批涉及代码/Lab 变更）
