# Lazy 语义：延迟的到底是什么

lazy 最容易被误读成“别在启动时创建”。实际语义更细：它可能延迟的是 bean 创建，也可能延迟的是某个注入点的依赖解析，甚至只是让注入点拿到一个代理。

## 三种常见语义

| 写法 | 主要延迟什么 | 典型结果 |
| --- | --- | --- |
| BeanDefinition lazy-init | 非懒 singleton 的预实例化 | refresh 时不主动创建，首次访问才创建 |
| `@Lazy` 标在 bean / `@Configuration` 产物上 | bean 的实例化 | 容器可跳过启动期主动创建 |
| `@Lazy` 标在注入点上 | 依赖解析和实际目标获取 | 注入点拿到的是延迟解析代理 |

这三者都被叫 lazy，但它们延迟的层次不一样。把它们混为一谈，会导致你以为“加了 `@Lazy` 就一定不会出错”，或者“加了 `@Lazy` 就一定不会创建对象”。

## BeanDefinition lazy-init：主要影响预实例化

`lazy-init` 最明确的作用窗口是在容器 refresh 的非懒 singleton 预实例化阶段。该阶段容器会主动创建大多数 singleton；被标为 lazy 的 bean 会被跳过。

但这不是绝对“永不创建”。在普通 eager 依赖解析中，如果它被其他 Bean 作为直接依赖需要、被显式 `getBean()`，或者被某些顺序要求提前触发，它仍然会被创建。

这里要排除一个重要反例：如果依赖方的注入点本身标了 `@Lazy`，容器可以先注入延迟解析代理，而不是立刻创建目标 Bean。也就是说，BeanDefinition lazy-init 关注“目标 Bean 是否参与预实例化”，注入点 `@Lazy` 关注“这条依赖边是否马上解析真实目标”。

所以 lazy-init 解决的是“是否在启动末尾主动创建”，不是“这个 bean 永远延后”。

## `@Lazy` 标在注入点：延迟的是依赖解析

注入点上的 `@Lazy` 更像是把依赖获取包装成一个按需入口。调用方在构造或字段注入时拿到的不是立即解析出来的目标，而是一个延迟获取的引用。

这对避免循环依赖很有用，但它也会改变异常暴露时机。原本在启动期就会报出的缺失依赖，可能被推迟到第一次方法调用。

`SpringCoreBeansLazyLabTest` 里应当把这个边界和普通 lazy-init 分开理解：一个是“这个 bean 是否在启动时创建”，另一个是“注入点拿到的是不是直接目标”。

## 循环依赖与异常时间点

lazy 经常被当成循环依赖的缓冲垫，但它并不自动修复所有循环。

- 如果循环依赖需要早期引用，lazy 只能影响某些创建时机
- 如果依赖真正缺失，异常可能只是从启动阶段后移到首次访问
- 如果目标对象根本不存在，延后并不会消灭错误，只会换一个时间点报错

因此 lazy 的价值不在于“隐藏问题”，而在于“把问题放到更合适的时机暴露”，前提是你知道那个时机是什么。

## 启动性能的边界

lazy 可以减少启动期工作量，但它不是免费的。

- 启动会更快一些，因为少了一部分预实例化
- 首次访问会更慢，因为成本被推迟过去了
- 如果 lazy bean 最终一定会用到，总成本未必更低，只是换了时间点

所以是否使用 lazy，要结合访问模式看。如果 bean 几乎总会在启动后马上被用到，lazy 未必有收益；如果只有少数路径需要，lazy 才更像真正的收益点。

## 看到 lazy 时，先问它落在哪一层

- 是 bean 定义上的 lazy-init
- 是 bean / config 上的懒加载标记
- 还是注入点上的延迟获取

这个判断决定你该看启动阶段、依赖解析阶段，还是首次调用阶段。
