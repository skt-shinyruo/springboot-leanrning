# Doc Writing Booklike（书稿式：按知识点写，不按栏目写）

## Overview

这套写法的“灵魂”不是排版，也不是栏目齐全，而是：**用一条真实的入口把读者带进源码，然后用对象/分支把他带出来。**

你写的不是“概念解释”，更像是一次把源码跑清楚的讲解：每个小节都能回答一个具体问题，并且能指向一个具体落点（类/方法/分支条件/异常/关键变量）。

**硬规则：禁止用固定栏目套模板。**  
可以出现“导读/总结/实验”这类词，但它们只能当标签，后面必须跟具体知识点（例如 `导读：BeanDefinition 覆盖影响的到底是哪一层`），并且整章标题不能被这些栏目词覆盖掉。

## Non‑negotiables（别再写回“规范体”）

- **标题跟着知识点走**：对象 / 方法 / 分支 / 失败点 / 边界，至少占一个。纯栏目标题（`## 导读` 这种）不行。
- **深度要落到“分支决定”**：解释到能定位“在哪个方法的哪个判断做了决定”，而不是解释到能背概念。
- **语气可以像人**：允许提问、类比、插一句作者口吻；但 1–3 句内必须落回一个锚点（类/方法/调用链/变量/异常）。
- **密度靠“可对照”承载**：用类名、方法名、调用链、图/表去压缩解释；别靠“很重要/建议/注意”撑篇幅。

## 先选“主线”（你这章到底沿着什么往下讲）

不要默认“导读/机制/实验/小结”。先选你这一章的主线是什么，标题自然会跟着主线长出来：

- **调用链主线**：你要讲“从入口一路跑到落点”。主标题/小标题就直接用链路里的对象或关键方法命名。
- **决策树主线**：你要讲“为什么走这个分支、另一个分支什么时候发生”。标题就点名“分支条件 + 落点”。
- **对象族谱主线**：你要讲“接口/抽象类下面有几类实现，谁负责什么”。标题就点名“角色/职责/差异点”。
- **时机主线**：你要讲“这件事发生在注册期/加工期/实例化期的哪个时刻”。标题就点名“时机 + 触发点”。
- **失败点主线**：你要讲“某个异常/不生效/奇怪现象到底卡在哪里”。标题就点名“异常/现象 + 触发条件”。

一章只要主线清楚，结构就不会像模板；反过来主线不清楚，再多栏目也只是糊墙。

## 每个小节只解决一个“知识点”，并把它写到能复核

把小节当成“一个知识点卡点”的解决方案，写法随知识点变，不要套统一格式。常见知识点类型与落点提醒：

- **对象/角色类知识点**：它的职责边界是什么？谁调用它？关键字段/不变量是什么？
- **分支/规则类知识点**：分支条件是什么？为什么会这样判断？走不同分支会造成什么外部现象？
- **边界/误判类知识点**：哪些看起来相关其实不相关？读者最容易在哪一步误判？
- **对照/取舍类知识点**：A vs B 真正差在哪（时机/语义/失败点/观测入口），用表或简图把差异压缩出来更划算。

写完一节，读者应该能回答两句话：**“我去哪个类/方法打断点？”**、**“我看哪个变量/条件确认分支？”**

## 证据怎么选（不是三件套，是按知识点挑合适的载体）

表/图/调用链都可以用，但它们不是“为了显得专业”，而是用来压缩解释成本：

- **调用链**：讲“怎么一路走到这里”，最省字。
- **图示**：讲“对象关系/线程关系/层次结构”，比文字可靠。
- **对照表**：讲“差异点很多但都短”，用表最稳。

别为了凑形式硬塞；当你发现一段解释越写越长、读者越看越晕，才是该上图/表/链的时候。

## 工具：把 lint 当成提示器，不当闸门

- Run: `python3 skills/doc-writing-booklike/scripts/doc_phrase_lint.py <file...>`
- 默认只给提示（exit code 恒为 0），用来提醒“是不是又写回模板标题/是不是锚点太少”。
- 如果你真想把它当闸门用：加 `--gate`；需要更严格再叠 `--strict`。
