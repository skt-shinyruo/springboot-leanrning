# 书稿式章节：写法约束（面向本仓库）

这份参考只定义“落地约束”，不讲写作理论。目标是把章节写得更像 `reference/zhihu_456835010/zhihu_456835010.md`：知识点驱动、对象密度高、图表对照充分、作者口吻但不虚。

## 1) 标题：跟着知识点走

标题要让读者一眼看出“这一节在讲哪个对象/分支/失败点”，而不是只看见栏目名。

判断标准（最实用）：**如果一个标题放到别的章节也完全不违和，它大概率就是模板标题**。

### ✅ 好标题（知识点）

- `## EventLoop：IO 就绪事件是谁在轮询？`
- `## openSelector：Selector 是怎么被创建并被包装的？`
- `## allowBeanDefinitionOverriding：允许覆盖 vs 禁止覆盖的失败点`

### ❌ 坏标题（模板）

- `## 导读` / `## 机制` / `## 实验` / `## 小结`

如果确实要用栏目词，必须写成“栏目：知识点”（例如 `## 总结：覆盖只影响定义注册阶段`），并且栏目标题不能占多数。

## 2) 内容密度：用“可对照的东西”承载解释

章节不需要凑“三件套”，但要在最难讲清楚的地方放一个“可对照的东西”，否则文字很容易变成空泛解释：

- **对照表**：A vs B（语义/时机/失败点/观察入口）
- **图示**：图片 / mermaid / dot（对象关系或调用流）
- **调用链**：`A#x -> B#y -> C#z`（或同等清晰的链路表达）

要求不是“形式齐全”，而是“读者可以拿着它去复核”。

## 3) 深度：至少写到方法级/分支级

所谓“知识深度”不是把概念讲得更长，而是把关键判断落到“分支条件与落点”：

- 哪个方法里做决定（入口）？
- 分支条件是什么（为什么进/为什么不进）？
- 失败点在哪里（抛什么异常 / 返回什么值 / 缓存了什么）？
- 读者怎么复核（断点/断言/输出字段/最短命令）？

如果一段话里只有名词而没有对象落点（类/方法/变量/异常），就不够深。

## 4) 作者口吻：允许，但必须“落回对象”

允许提问、类比、穿插解释（甚至带一点“笔者视角”）。但类比与提问必须服务于理解，并且要在 1–3 句内落回一个对象锚点（类/方法/调用链/表格/图示）。

不推荐依赖这些空话来“显得重要”：

- `显然`、`众所周知`、`很重要/非常关键`（如果真重要，直接写失败点与复核入口）

## 5) 可运行与可回归：入口要写到“能跑一次就看到现象”

- 入口优先 `mvn -pl :<module> -Dtest=<TestClass> test`（参数写全，不用省略号）。
- 入口后面写清楚观察点：2–3 个断点/变量/断言/输出字段（稳定且可复核）。

## 6) 最快自检（2 分钟）

- 标题是否以知识点命名（对象/分支/失败点），而不是模板栏目？
- 是否至少做出一类“可对照的东西”（表 / 图 / 调用链）来承载解释？（能做到两类更稳，但不要为了凑数硬塞固定结构）
- 关键结论是否能落到断点/断言/变量/输出字段？
