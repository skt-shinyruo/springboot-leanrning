# spring-core-beans Docs “说人话”改写设计

**Goal：**把 `spring-core-modules/spring-core-beans/docs` 的正文从“模板化清单/元叙事/术语堆叠”改成更接近教材式的连续叙述，让读者更快回答：这章解决什么、怎么验证、下一步去哪读。

**范围：**

- 仅改写 `spring-core-modules/spring-core-beans/docs/*.md`
- 不改动 Java 代码与测试（除非发现文档引用的入口不存在或明显错误）
- 不改动文件名与整体导航结构（避免破坏现有链接与锚点）

---

## 1. 背景与问题陈述

当前 spring-core-beans 文档已经具备本仓库的关键特性：**可运行、可验证、可回归**。但在阅读体验上仍存在几个“AI 味/工程味过重”的问题：

1) **导读段落模板化**：大量页面的导读开头重复“本章围绕…展开/目标是…”，信息密度偏低，读者很难从第一屏判断“这章什么时候用得上”。
2) **元话术过多**：例如“建议先…再…”重复出现，但缺少更具体的“现象→证据→结论”连接词，读感更像规范说明而非教材。
3) **关键信息被稀释**：入口命令、观察点、误判对照存在，但容易被重复段落覆盖，导致“看完没记住能用什么验证”。

---

## 2. 目标（验收口径）

改写完成后，读者打开任意一页，应当能在 30 秒内回答：

1) 这页在解释哪个现象/解决哪个问题？
2) 这页给的“事实入口”是什么（Lab/命令/观察点）？
3) 读完后下一步去哪里（同模块下一章/最短跨模块跳转）？

同时必须保持：

- **证据链不丢**：方法名、断点入口、关键变量、Lab 名称保持一致；结论能回链到“入口方法 + 关键分支/变量”。
- **导航不破坏**：不大改标题层级；不改文件名；尽量不改已被引用的锚点（尤其是 guide/appendix 的锚点）。
- **口吻一致**：继续使用第三人称中性教材腔（“读者/建议/应能够”），但减少空泛铺垫与口号式总结。

---

## 3. 非目标（明确不做）

- 不追求把每章变成“百科全书式完整覆盖”，重点是可读性与可验证性。
- 不引入新的文档体系/新的导航 SSOT；模块内部仍以模块 README 与现有 appendix/guide 作为入口。
- 不把所有章节统一重排成同一套固定栏目（避免“规范文档化”读感与维护成本上升）。

---

## 4. 改写策略（推荐）

采用“微创说人话 + 开头三句话”的组合：

1) **微创说人话（主策略）**
   - 不改骨架，只改“导读/解释段落/误判对照/决策表”中最模板化、最元叙事的句子。
   - 把“本章围绕…展开/目标是…”改成更具体的“这一章回答一个问题：X 为什么发生？用哪个入口验证？”
   - 优先写清楚“什么时候会用到这章”，而不是“这章会讲什么”。

2) **开头三句话（可选增强）**
   - 在导读或机制主线前增加极短的“TL;DR（≤3 句）”，帮助读者在第一屏抓住方向。
   - TL;DR 必须能回链到本文的实验/断点入口。

所有改写遵循 `docs/writing-style-guide.md`：

- 用“现象 → 解释 → 验证”推进段落
- 少元叙事，少模板化标题，减少空泛推荐句
- 保留并强化“可运行入口/观察点/下一跳”

---

## 5. 分批提交策略（Batch）

全目录按主题分批改写，每批一个 commit，保证可审阅/可回滚：

1) Batch 1：Guide + Appendix 导航页（先把“入口怎么用”说人话）
2) Batch 2：IoC Container（注册/注入/生命周期主线）
3) Batch 3：Container Internals（refresh→创建链路、processors、early reference）
4) Batch 4：Wiring & Boundaries（候选选择、代理、值解析、类型转换等边界）
5) Batch 5：AOT + Boot + Real World（契约/Reader/输入层/工程落地）
6) Batch 6：Deepening 系列（把“加深建议”改成更可执行的路线）

---

## 6. 风险与回滚

主要风险：

- 大范围文本修改导致审阅成本上升（用分批 commit 控制）
- 不小心改动标题/锚点导致跳转失效（默认不动层级；必要时小范围调整并检查引用）

回滚方式：

- 每批一个 commit；若某批改写不符合预期，可直接 `git revert <commit>` 回退该批而不影响其他批次。
