# Round 2（入口页/工具页继续深化）：具体落地策略清单（按文件）

说明：本文件用于把 `helloagents/plan/202602011503_beans_docs_deepen_round2/` 的目标变得更可执行。
- 重点不在“再写一套方法论”，而在“让读者下一步动作更明确、更可验证”。
- 以入口页/工具页为主：优先让读者从“现象/目标”直接进入“对应章节 + 对应 Lab/Test + 对应断点组”，而不是再次顺读全章。
- 行文约束：保持现有 beans docs 的教材化书面语风格（避免第二人称与口语化措辞），只在确实降低成本处补充说明。

---

## 1) `spring-core-modules/spring-core-beans/docs/README.md`（Docs TOC / 入口页）

### 当前已有资产（基于现状观察）
- 已包含：
  - “如何运行（最小闭环）”与模块级运行命令
  - “可从此处开始”入口列表（Why Index / Quickstart / Deep Dive / Deepening Strategies / Knowledge Map / Debugger Pack / Training Kit）
  - “症状驱动导航（快速定位）”表（现象 → 最短章节）
- 但入口仍偏“资源列表 + 分散跳转”：读者进入下一轮加深时，仍需要自己把“章节 → 断点/验证动作”拼起来。

### Round 2 的补强重点（建议落地）
1. **把入口从“列资源”升级为“给路径”**
   - 新增一个非常短的“继续深化从哪里开始（Round 2）”段落（位置建议：紧贴“可从此处开始”之后）。
   - 用 2–3 条“选择题式分流”描述读者的当前状态，并给出最短下一步动作：
     - **现象驱动**：先去 `appendix/03-knowledge-map.md` 定位“现象→章节→断点入口→Lab”，再回到对应章节阅读主线。
     - **断点驱动**：先看 `part-00-guide/07-breakpoint-map.md` 挑 1 组断点（C1–C7），再用本模块已有 Lab 把变量变化观察到。
     - **生产排障驱动**：先走 `appendix/05-production-troubleshooting-checklist.md` 的最短 SOP，把问题分型为定义层/实例层/代理替换/值解析，再回链到章节与用例。
2. **在“症状驱动导航”表旁补“下一步验证”的统一指向**
   - 不需要把表格做得更大；建议在表格上方或下方补一句固定提示：
     - “定位到章节后，下一步建议跳到知识地图/断点地图挑入口（链接）”
   - 原则：避免把 README 变成另一个知识地图；README 只负责“把读者送到正确的下一跳”。

### 风格注意事项
- README 作为目录页：以“指路”为主，避免扩写机制细节（机制细节留在章节正文/Why Index）。
- 每条“下一步建议”都尽量落到可执行动作（跑哪个用例/看哪个断点组），而不是抽象表达。

## 2) `spring-core-modules/spring-core-beans/docs/deepening-strategies/README.md`（策略入口）

### 当前已有资产（基于现状观察）
- 已完成降模板化：强调“挑本章最缺的拼图”，并用“可复现 + 可证明 + 可复述”做自检。
- 但仍缺少两种“反向入口”的明确说明：
  1) “只知道现象，不知道章节”的读者怎么用策略？
  2) “从工具页过来”的读者怎么回到章节里落地？

### Round 2 的补强重点（建议落地）
1. **补齐两种入口的使用方式（不是新模板，是两条路径）**
   - **从现象进入**：建议把入口锚定到 `appendix/03-knowledge-map.md`：
     - 先在知识地图定位章节与推荐 Lab/Test
     - 再回到章节正文末尾的 `AE-DEEPENING`（或章节配套 Lab）继续加深
   - **从断点进入**：建议把入口锚定到 `part-00-guide/07-breakpoint-map.md`：
     - 先选断点组（C1–C7）确定处于 refresh 的哪一段
     - 再回到对应章节，用策略文档帮助“把观察收敛为结论/反例/排错路径”
2. **把“策略文件索引”前置成“从哪里开始（短版）”**
   - 不改变现有索引结构，只是在索引前补 2–3 行“最短开始路径”即可。

## 3) `spring-core-modules/spring-core-beans/docs/appendix/03-knowledge-map.md`（知识地图）

### 当前已有资产（基于现状观察）
- 已提供：
  - “核心七件套”与推荐 Lab/Test
  - “现象 → 章节 → 最短断点入口 → 推荐 Lab”表
  - 误归因对照与顺读路线
- 断点入口目前多为“方法名字符串”，但缺少“对应断点组/对应断点地图位置”的回链。

### Round 2 的补强重点（建议落地）
1. **给“最短断点入口”补一个稳定的落点**
   - 让读者从知识地图能直接跳到断点地图的对应组（例如 C6 注入解析、C7 after-init 代理替换、C5 doCreateBean 主线等）。
   - 建议方式（选其一即可，避免过度工程化）：
     - A）在断点地图中为 C1–C7 增加稳定锚点（HTML anchor），知识地图表格在断点列直接链接过去
     - B）不改锚点：在知识地图里新增一列“断点组（断点地图）”，填 `C6/C7/...` 并链接到断点地图对应小节
2. **把“推荐 Lab”改为更可直接执行的入口（在少数关键行补充即可）**
   - 对最常见的 3–5 个现象（注入歧义、循环依赖、代理不生效、@Value、FactoryBean），在推荐 Lab 单元格中优先引用“更接近现象的用例入口”（如果已经存在具体方法名/测试类）。
   - 原则：不要求每行都升级；只做高频项，保持表格可读。

## 4) `spring-core-modules/spring-core-beans/docs/part-00-guide/07-breakpoint-map.md`（断点地图）

### 当前已有资产（基于现状观察）
- C1–C7 已按 refresh 时间线组织，且每段都有“入口断点/观察点/决定性分支”。
- 但断点地图作为“工具页中枢”，仍可更明确地回答一个问题：
  - “从知识地图/排障清单跳过来后，应该选哪一组断点？”

### Round 2 的补强重点（建议落地）
1. **新增一个极短的“从症状选择断点组”分流（放在导读或 C1 前）**
   - 只覆盖高频 5 类即可（定义注册/注入歧义/循环依赖/代理替换/@Value）。
   - 每类给出：
     - 对应断点组（C2/C6/C5/C7/…）
     - 对应知识地图入口（回链到 `appendix/03-knowledge-map.md` 的相关行或章节）
2. **为 C1–C7 增加稳定锚点（可选，但建议）**
   - 目的不是“美化”，而是让知识地图与排障清单能稳定链接到断点组。
   - 原则：只加锚点，不改变章节结构与编号，避免造成阅读习惯变化。

## 5) `spring-core-modules/spring-core-beans/docs/appendix/05-production-troubleshooting-checklist.md`（生产排障清单）

### 当前已有资产（基于现状观察）
- 已有：
  - “总分流表（现象→阶段→第一断点→第一章→推荐 Lab）”
  - “排障 SOP（Symptoms/Repro/Evidence/Decision/Fix/Verify）”
  - “常见事故分类（2.x）”并给 Evidence/Docs
- 但 2.x 分类仍偏“说明书式”，下一步动作可以更短（尤其是在读者已经有“现象”时）。

### Round 2 的补强重点（建议落地）
1. **为最常见 3 类事故写成“最短诊断路径（3–5 步）”**
   - 优先挑：
     - 注入失败（NoSuch/NoUnique）
     - 代理不生效（时机/顺序）
     - 循环依赖/early reference（constructor vs setter、early vs final）
   - 每条路径建议包含：
     - 第一步：定位阶段（链接到断点地图 C1 或对应章节）
     - 第二步：第一断点（链接到断点地图对应组）
     - 第三步：最小观察点（3 个变量/对象快照）
     - 第四步：最短下一跳（链接到对应章节与对应 Lab/Test）
2. **把“总分流表”与“知识地图”形成互链**
   - 生产排障清单的分流表是“生产视角”，知识地图是“学习/复盘视角”。
   - Round 2 建议在分流表附近加一句：需要更系统的“现象→章节→断点→Lab”索引时跳到知识地图（链接）。
