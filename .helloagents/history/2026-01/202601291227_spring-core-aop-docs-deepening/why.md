# 为什么要做逐章“深度完善”

## 背景

- `spring-core-modules/spring-core-aop` 目前已经具备一套 “docs + 可运行/可调试的 Lab Tests” 的学习载体，但各章节在「主线解释」「关键分支」「验证闭环」「排障套路」上的深度与密度不完全一致。
- Spring AOP 的理解成本不主要在“概念多”，而在“实现路径长 + 分支多”：JDK vs CGLIB、自调用、final 限制、AutoProxyCreator 的分支、以及多代理叠加等。
- 因此，本次完善不以“固定补哪些模块”为目标，而是以“读完每个章节后，针对本章真实问题域补强”作为推进方式。

## 为什么要按“章节内容”逐一补强

- 每章的“问题域”天然不同：有的偏心智模型（mental model），有的偏源码主线（AutoProxyCreator mainline），有的偏调试与排障（breakpoint map / common pitfalls）。
- 如果强行套统一硬标准，容易出现“格式统一但不解决本章痛点”的堆料；看似更厚，实则更难学与更难验证。
- 逐章补强的目标是：让读者在本章结束时能回答并做到——
  - 发生了什么？（主线）
  - 为什么会这样？（机制）
  - 怎么验证？（断点/日志/测试）
  - 出问题怎么排？（分支/坑位/决策树）
  - 与下一章怎么连？（跨章复用）

## 产出与预期收益

- 产出
  - 每章“补充 + 完善 + 深入”的具体策略（见 `chapters/*.md`）
  - 可执行的落地任务清单（见 `task.md`）
- 预期收益
  - 读者更容易建立“从现象 → 断点/日志 → 源码 → 结论”的闭环
  - 各章节形成可复用的公共资产：时间线、断点地图、分支矩阵、坑位索引、自测题
  - 降低“看懂了但调不出来/做不出来”的断层，提升学习效率与可迁移能力
